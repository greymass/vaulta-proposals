## What this is

Work the VST and VS LLC administer themselves, which the Network does not vote on.

MSIG #5 and the RFP Framework each carry a list of what is still to be settled. Those lists hold only what **block producers decide or must see filled** before the program can run. This register holds the rest: drafting, execution, handovers, and sourcing that has to happen but is nobody's vote.

**It is not an attachment to MSIG #5. It is not approved by MSIG. It is not published on-chain.** Nothing in it conditions the Resolution, and nothing in it can change what the Resolution says. Where an item here turns out to need a Network decision after all, it moves **out** of this register and into the MSIG blanks list or Framework Appendix C — that is the only way it acquires any force.

**Why it exists separately.** A governance instrument that tracks its own administrative chores invites block producers to vote on them. They should vote on the mandate, the limits, and the people. Whether counsel has finished a conforming amendment, or whether a repository has moved, is a matter for the parties doing the work — and burying it in a Resolution neither makes it happen faster nor makes the Resolution better.

## 2. EOS Rio code and rights handover

**Owner:** VS LLC, with EOS Rio
**MSIG dependency:** none. Framework 15.2a records that the platform is VST-owned; EOS Rio has committed to transferring the code and the rights, and that commitment is accepted. What remains is paperwork.

| Item | Detail | State |
|---|---|---|
| 2.1 | **Executed assignment** of the existing platform code and rights to the VST | Open |
| 2.2 | **Contributor coverage** — confirmation the assignment reaches every contributor, not only the contracting entity | Open |
| 2.3 | **Repository transfer** into a Network-controlled account, with credentials, domains, and documentation | Open |
| 2.4 | **`disc.vst` registers** — disclosures (Framework 6.3b) and decisions (7.6a), to be built and serviced by EOS Rio. *This one has a live MSIG counterpart at blank 9 and Framework Appendix C item 8, because the Program Account is not funded until the Exhibit D configuration covering them is published* | Open — **blocking, tracked in the MSIG** |
| 2.5 | **The initial build is an award** (Exhibit D Part 5, Framework 15.2b). Settled. What this register tracks is the sequencing it forces — see the note below | Open |

**How an award for work that precedes the program actually runs.** The decision is made: the initial build of the RFP platform, including both `disc.vst` contracts, is an **award** under Framework 15.2b — Core Development, against the Cycle Ceiling, flagged self-referential in the cycle report. Five things follow from awarding it for work that will already be under way.

| | |
|---|---|
| **It cannot be awarded before the Committee exists** | An award needs a seated Committee, a funded Program Account and a Manager of record. The Program Account is not funded until Exhibit D is published, and Exhibit D describes contracts that have to be deployed first. **Whoever builds, builds before the award exists** — so either the builder carries that risk knowingly, or the VST bridges it and is reimbursed by the award. That is a commercial conversation to have **before** the work starts, in writing |
| **It is sole-source, and that makes it a reserved matter** | Framework 15.2b: where the Committee records that **no other capable provider exists**, the award is a **reserved matter** requiring an MSIG Resolution. Nobody else has the code or the context, so expect to record exactly that. As a **bounty** the equivalent is 26a rule 14 — the expectation is recorded and published at publication, with reasons |
| **It still needs two milestones** | Framework 11.1a has no exception for work already done. This is workable rather than awkward, because real work does remain: a first milestone on **source delivered into a Network-controlled repository with the copyright assignment executed**, a second on **deployment, documentation and handover**. Both are inspectable, which is what 20.2 asks of a milestone |
| **It will consume a visible share of the first cycle** | Against a Cycle Ceiling of USD 150,000, an award in the range discussed takes roughly a quarter of the first cycle's capacity — and it is the program's **first award**, spent on itself. That is defensible and it is also exactly the number the self-referential flag exists to surface. Better said out loud now than discovered in the first cycle report |
| **VS LLC may not bid** | Framework 15.2b bars VS LLC and anything connected to it from bidding on RFP-system work. It operates the system, holds the code and deployment access, contracts the awardee, runs the Portal and performs the 15.3 refusal check. An external builder raises none of this; a VS LLC-connected one would need an MSIG waiver at the Threshold with published reasons |

**Why 2.1–2.3 are not blocking.** The program can publish RFPs and make awards on a platform whose assignment paperwork is still in flight. What it cannot do is treat the platform as VST-owned in a cycle report before it is. The risk of leaving these untracked is not that the program stalls; it is that a year passes and nobody notices the assignment was never signed.

## 3. Candidate sourcing for the four seats

**Owner:** Anyone. This is deliberately not assigned.
**MSIG dependency:** none. MSIG #5 Part B sets the process, the eligibility tests, and what makes an Exhibit E proposal complete. **It names no candidates, by design** — who is proposed is a separate decision, made in a separate Resolution, at the Threshold.

| Item | Detail | State |
|---|---|---|
| 3.1 | Candidates for **Core Development**, **Marketing**, **Business Development**, and **General (At-Large)** — individually, as a full slate, or in any subset | Open |
| 3.2 | Whether any proposal is put forward **all-or-nothing** rather than seat-by-seat, where candidates were chosen to balance each other | Open |
| 3.3 | Network vision statements — **written by the candidate**, not the proposer, and not something a proposer can supply on their behalf | Open |

**What this register is not.** It is not a shortlist, a nomination, or a queue. Recording a name here would give it a standing MSIG #5 does not confer, and VS LLC does not decide who is eligible (Part B). Use it to track that the work is happening, not to do it.

**The program supplies its own pressure.** Until all five seats are filled and every member has signed, filed, and registered a key, the Program Account is not funded, no RFP is published, and no award is made. No date is set for filling the seats because that timing rests with block producers.

## 4. How an item leaves this register

| Route | What it means |
|---|---|
| **Done** | Struck through with the date and the evidence — the executed document, the transaction, the published exhibit. Unlike the MSIG blanks list, closed items stay visible here; this is a working record, not an instrument |
| **Escalated** | It needed a Network decision after all. It moves to the MSIG blanks list or Framework Appendix C, and this register keeps a pointer |
| **Dropped** | With a reason. An administrative task nobody is doing should say so rather than sit open |
